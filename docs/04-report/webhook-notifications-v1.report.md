외부 시스템(Slack/Teams/사용자 정의 서비스)이 Server_API의 도메인 이벤트를 풀(poll) 없이 푸시로 수신할 수 있는 표준 채널을 신규 도입. HTTP Webhook 등록·발송·이력 관리 인프라와 내부 `emit_event` 헬퍼를 추가했으며, 기존 라우트·도구·OpenAPI 스키마에는 변경을 가하지 않음.

## 9. Lessons Learned

1. **분리된 SQLite DB는 ERP 재배포 시나리오에서 강력**. production_analysis.db는 외부 파이프라인이 주기적으로 덮어쓰는 자산. 알림 메타를 그 안에 두면 retention 정책 충돌 발생. 새 도메인을 추가할 때마다 "이 데이터의 소유자가 누구인가"를 묻고 답이 다르면 DB를 분리하는 패턴이 안전.

2. **`transport` 매개변수 = 깨끗한 test seam**. dispatcher가 `httpx.BaseTransport`를 받도록 한 단 한 줄의 결정으로 통합 테스트가 외부망 0건, 모든 응답·실패 시나리오 제어 가능. AI 도구 호출(`_gemini_client`)에도 같은 패턴 도입 검토 가치.

3. **dispatcher가 절대 raise하지 않는다는 규약은 emit_event를 "fire-and-forget"으로 만든다**. 호출자(향후 ERP intake hook 등)가 try/except 없이 한 줄로 호출 가능. v2의 async worker도 같은 규약을 유지해야 함.

4. **AC11처럼 "net 추가 라인 ≤ N"을 명시하면 main.py 비대화를 강제로 막을 수 있다**. 라우터 분해 사이클 이후 main.py가 다시 부풀지 않도록 모든 사이클에서 동일 게이트를 적용 가치 있음.
