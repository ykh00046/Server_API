## 1. Summary

`webhook-notifications-v1`의 동기 1회-시도 발송을 **백그라운드 워커 큐 + exponential backoff 재시도**로 확장. `emit_event`는 기본 async — 호출자에게 즉시 반환되며, 단일 daemon thread `WebhookDispatchWorker`가 SQLite `webhook_deliveries` 테이블을 큐로 사용해 due rows를 claim → dispatch → finalize. 5xx/네트워크 실패는 1·5·25·125·625s 지수 backoff(±20% jitter)로 자동 재시도; 4xx는 즉시 영구 실패; `Retry-After` 헤더가 있으면 그 값 우선; `MAX_ATTEMPTS` 초과 시 `dead`.

신규 라우트는 운영 가시성용 2개만 추가(`/queue/stats`, `/deliveries/{id}/retry`). `emit_event(sync=True)`로 v1 호환 경로 보존. 신규 외부 의존성 0.

## 9. Lessons Learned

1. **`tick_once()` 공개는 비동기 워커 테스트의 황금률**. 백그라운드 thread를 직접 sleep로 기다리는 테스트는 본질적으로 flaky. tick을 한 번씩 명시적으로 호출하는 인터페이스를 워커에 두면, 모든 시나리오를 결정론적으로 검증 가능. AI tool dispatcher / Gemini 비동기 호출 같은 다음 worker-pattern 도입 시도 동일 패턴 차용 권장.

2. **`random_fn` DI는 jitter를 결정론으로 만드는 가장 가벼운 도구**. 별도 패치 모듈, monkeypatch, freezegun 없이도 `lambda: 0.5`만 넘기면 jitter=0. backoff/Retry 로직을 추가하는 모든 후속 사이클은 이 패턴 표준화 가치.

3. **SQLite를 큐로 쓰는 단일-워커 모델은 MVP에 충분**. WAL + thread-local conn + `BEGIN IMMEDIATE`만으로 race 0, 영속성 자동, 외부 의존성 0. 트래픽이 진짜 늘기 전까지 Redis/Celery 도입은 premature. 사용자 부담을 늘리지 않는 게 핵심.

4. **AC를 "추가 라인 ≤ N"으로 명시하면 코드 비대화를 정량적으로 막을 수 있지만, 첫 시도에서 자주 미달**. 본 사이클은 1회 iterate로 +20 → +12로 줄였음. design 단계에 라인 카운트 모의 추정을 의무화하면 iterate 회피 가능. `api-router-split` (98%, 2026-05-22)의 main.py ≤ 250 lines AC도 동일 교훈.

5. **마이그레이션 idempotent 패턴은 운영 DB가 있는 모든 사이클의 기본기**. `PRAGMA table_info` → `ADD COLUMN` 분기는 SQLite에서 가장 안전. v1 배포 후 v2를 별도 마이그레이션 도구 없이 lazy-init만으로 적용 가능 — 이 패턴을 `webhook-housekeeping-v1` 같은 후속 사이클에도 그대로 차용.
